The "diagram-as-UI" arc: make text, buttons, input fields first-class diagram entities placed on cells, so a control panel is itself a diagram — the same primitives for UI as for content. This page compares 4 candidate approaches to the foundational text entity (each also mocking a button, an input, and a reconstructed control bar to test generalization), with an independent judge's scored verdict.

▸ Judge's full reasoning + the parity-safe build order (click to expand) 
I've grounded the call in the actual code. Key verifications:

- **Node anchors on cell-centres** (`cellPx` = `cell·pitch`, multiples of 60); the `#m-square` frame is a centred `2·ext` square at the cell centre (`spec.mjs`, `renderer.mjs:80-82`).
- **Approach C's "stretched node" math checks out exactly**: frame inset `g = pitch/2 − node = 10`; at `cols=1`, `x = c0·P − 20, w = 40` — pixel-identical to today's node. So C reuses the frame/ladder/CSS by *sharing geometry*, not by mutating the node entity.
- **Zone anchors on the half-offset grid** and resolves at ladder ext `29` (`engine.mjs:62-65`); its edges never coincide with node-label cell-centres → Approach A's even-span drift is real, not theoretical.
- **Approach B's panel recursion provably fails**: `endpointOf` = node|waypoint only (`model.mjs:109-111`), `expandSelection` resolves groups via it, and `SELECTABLE` excludes `group` — a group cannot contain groups, so "panel = group of widgets" is impossible.
- **Kernel currently defers ALL text**: `renderer.mjs` emits zero `<text>`; every label is an app-side pill with the `9px/char` metric (`app/src/renderer.js:22,106-119`). The metric to promote to the kernel already exists.
- **The server gate is strict and additive-friendly**: unknown-field (`validate.js:71`) and unknown-kind (`:65,88`) both 400, but the `OPTIONAL` set (`:61`) is the proven absent⇒default migration trick (`node.shape`). Any new kind/field MUST land in `validate.js` (KINDS, FIELDS, OPTIONAL, SELECTABLE regex, EXT) in lockstep or reload rejects the doc.

B is eliminated outright: a derived (never declared) box off both grids, waypoint overload that pollutes occupancy/routing, panel recursion that provably fails, and a split text regime that only half-achieves "first-class text." A is eliminated for the wrong grid (half-offset), back-most z-order by default, and the eye-catching even-span misalignment against node labels — fatal for a control bar that must align with diagram content.

That leaves **C vs D**. On pure aesthetics D wins the raw sum, driven entirely by unification: one placeable thing, canvas and toolbar literally the same substrate. But that exact strength is what makes it the wrong *first* move.

## WINNER: Approach C — the new `text` KIND. (D is the north star; C is the de-risked path to it.)

The deciding factor the scoring table doesn't capture is **blast radius / parity-safety**, which the prompt explicitly demands ("first-pass", "parity-safe path"). D turns `node` — the single most-consumed, already-shipped entity — into a tagged union. Every `if (kind==='node')` site (renderer `update()`, GRC, occupancy, schema, *link-endpoint connectability*) must branch on `content`/`span` or silently mishandle a widget, and the whole migration hinges on absent-content⇒glyph holding across all of them. That is concentrated risk in the load-bearing path of a working diagram.

C gets ~90% of D's reuse via the verified "node is the degenerate 1×1 case" identity — it **shares the frame template, ladder, frameR and `.frame` CSS without overloading the node entity**. The shipped glyph-node path stays byte-for-byte (`renderEl` node branch verbatim; single-cell node occupancy unchanged). Both C and D anchor on the correct cell-centre grid, both move text into the kernel, both need footprint occupancy + a rectangular `selBox`. C buys all of that on an *isolated* kind. And critically: **once C's text atomic + footprint occupancy + rectangular selection are proven on the isolated `text` kind, you already own every mechanism D needs** — collapsing `text`-node into `node`-with-`content` later becomes a refactor with the dangerous parts already de-risked. C is not a competitor to D's unification; it is the staged, parity-safe route to it.

## What to BUILD first — the text atomic + ONE entity (`role:'label'`), parity-safe

Ship the text atomic and the label entity *alone*. Defer button/input/bar/panel to a second pass once the atomic, selection, and occupancy are proven.

Build order, each step additive (existing kinds untouched, absent-`text` docs load unchanged):

1. **Promote the font metric to spec.** Move the `9px ASCII / 15px CJK` advance from `app/src/renderer.js:pillWidth` into `kernel/theme.mjs` as the sovereign metric, and add `TOKENS.text`/`textMuted`/`btnFill` + a `.widget` CSS block. This is the one load-bearing decision — the kernel deliberately acquires a single typography constant; treat it as locked like `pitch`.
2. **Text atomic in `kernel/renderer.mjs`.** A `text` resolved primitive + `renderEl` case: content-box = frame interior inset `HPAD=12`, `dominant-baseline:central` at the row centre, `text-anchor` from `align`. Pure render — test headless via `render()`.
3. **`engine.mjs` resolve `text` case** using the verified stretched-frame math (anchor = top-left cell-centre, grow right/down by whole cells). `bboxOf` 'text' → frame rect. `DRAW_ORDER.text = 6` (front of node) — this fixes A's z-order defect by construction.
4. **`app/src/schema.js`**: `text` branch in `docToSchema`/`schemaToDoc` (anchor = top-left cell-centre; span from `cols/rows`).
5. **`document/model.mjs`**: add `'text'` to `KINDS`, `KEY` (`texts`), `SELECTABLE`; add `makeText` + `spanFor` (the quantizer: `cols = max(1, ceil((textPx + 2·HPAD + 20)/pitch))`, reusing the promoted metric).
6. **`server/validate.js` in lockstep** (the wire gate): `FIELDS.text`, add to `KINDS`, the `SELECTABLE` regex, `EXT` bounds, and the `texts` collection. Without this every widget 400s on reload — non-negotiable, lands in the same commit.
7. **Footprint-aware occupancy** in `commands.js` + the index: a multi-cell text-node claims `cols×rows` cells. Today `occupiedAt` keys one cell (`n.x===p.x`, `model.mjs:132`); a span must register all its cells or it reads "free" on non-anchor cells.
8. **`selBoxRect(w,h)`** generalizing the point-symmetric `selBox` (`renderer.mjs:11`) to track the ladder radius at four corners of a non-square frame.

Ship 1-6 to get a selectable, persistable, kernel-rendered label that lands on the node grid and exports headlessly; 7-8 complete spanning. Then **button is a one-line role** (fill/stroke swap), and **input/panel are the second entity-shape pass** (input = content-box split into a left label + a right slot sub-rect with a `foreignObject` overlay for live typing; panel/bar = a wide `role:'bar'` backplane hosting child text-nodes on its interior cells — that is the diagram-as-UI payoff).

## Grafts from the runners-up

- **From D (the convergence plan):** after the `text` atomic is proven, re-express the deferred node NAME pill (`app/src/renderer.js`) as an *attached* kernel text-node. That collapses the transitional two-owner text regime AND is the exact bridge that lets you later fold `text` into `node`-with-`content` — i.e. arrive at D's full unification with the risk already retired.
- **From A:** the input treatment — opaque slot fill + caret + port squares on the slot edges so a value field reads as a first-class, *wireable* entity with connection sites; and the abutting-tile discipline for the control bar.
- **From A/B (cautionary, already designed-in):** C's top-left-cell anchor is what *avoids* A's even-span centring drift and B's 4px float — keep the doc `x,y` semantic documented as the anchor cell (not the geometric centre), or callers will mis-place.

Files that change: `kernel/theme.mjs`, `kernel/renderer.mjs`, `kernel/engine.mjs`, `kernel/geometry.mjs` (`bboxOf`), `app/src/schema.js`, `document/model.mjs`, `server/validate.js`, `app/src/commands.js`. Locked geometry (`kernel/spec.mjs`) is untouched — C adds no rung to the ladder.
